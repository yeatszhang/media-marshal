# 桌面模块边界重构设计

## Context

动机和范围见 [proposal.md](./proposal.md)。本设计按当前工作区源码核查，不把历史验收次数当作本轮结果。

- `apps/desktop/src/` 已区分 Main、Preload、Core worker、Sidecar Host 和 Renderer；`packages/contracts` 有公开与 internal 入口，现有检查保护部分进程边界。
- 首次审视时 `ingestion/pipeline.ts` 约 1,266 行、92 个方法；Core 有 54 个非测试文件直接导入数据库类型或实现。行数包含当前排版影响，仅作为发现依据，不作为精确复杂度指标。
- `modules/application.ts` 混合组装、命令及私有处理；`media.storage` 实际创建下载等业务服务。Main 的入口混合窗口、IPC 和生命周期。Renderer 的 `services.ts` 同时定义多个模型并组装应用。
- `cloud` 与 `sources` 共同使用同步收据和媒体库文件判断；`sync-receipts.ts` 又引用云端预览类型。把原目录原样搬进新的父目录不能解除这些耦合。
- 数据库当前为 v35，识别和同步的运行路径仍使用旧配置接管信息。Main 备份恢复目前接受较旧 schema，再依赖 Core 升级；停止迁移必须同步调整恢复准入。
- 当前主规格中「历史本地整理配置迁移」与本轮采用的 1.0 前策略冲突，本变更通过 delta 明确替换该场景。`shared-download-directory` 已要求设置是唯一目录编辑入口；重构沿用当前界面与此约束，不恢复其他规格旧描述中的逐来源目录覆盖入口。规格之间这项既有文字差异不在本轮扩大修改。
- 已有日志与其他业务改动正在进行。路径映射、行数和基线在实施第一个提交前复核；不得回退这些功能以达到本设计的静态数字。

## Goals / Non-Goals

**目标：**

1. 阅读一个功能时能从公开入口定位用例、状态、持久化与测试；新增功能无需默认修改多个中央大文件。
2. 确定每份持久业务事实的写入所有者，跨模块通过窄接口协作，并保持文件提交与业务记账的一致性。
3. 将可机械识别的越界和结构增长变成 CI 失败；无法自动证明的业务约束提供明确审查项与故障回归。
4. 分阶段交付，每个提交均能构建并运行相应测试；目标模块最终不依赖临时转发入口或存量豁免。

**非目标：**

- 不替换 Electron、React、DI 框架、SQLite 或现有解析器，不拆微服务或新增 workspace，不引入通用事件总线、ORM 和万能 Repository。
- 不重做产品导航、交互视觉或业务策略，不新增语言、平台、网盘或发行承诺。
- 不把当前状态机、成功收据、原卷校验、独占文件操作及崩溃恢复当成历史兼容删除。
- 不执行实际用户数据清理，不新增应用内重置入口；仅提供清楚的不兼容反馈和隔离验收方法。

## Decisions

### 1. 以业务模块组织 Core，基础能力单向下沉

保留包边界，在 Core 内采用以下职责结构。目录按已存在的业务责任划分，不要求每个模块复制一套空层级。

```text
packages/media-core/src/
  bootstrap/                 # Application、模块组装、进程请求调度、跨模块流程
  domain/                    # 名称、季集、匹配、模板等纯规则
  modules/
    configuration/           # 设置、目录授权事实、配置版本
    library/                 # 媒体目标身份、Emby 绑定、本机库内证据
    sync/                    # 来源同步、账号、云端/本地执行、成功收据
      cloud/                 # 远端目录、预览、下载、提交
      local/                 # 本地同步
      history/               # 收据、重新授权后的历史确认
    ingestion/               # 接入、识别、计划、COPY、批次
    corrections/             # 已整理资产单条与批量修正
    delivery/                # Emby 通知与收录核对
    retention/               # 下载副本清理、共享需求核对
  storage/                   # 数据库生命周期、基线 schema、事务能力
  files/                     # 授权路径、原卷、摘要、原子文件原语
  adapters/                  # parser、TMDB、HTTP 等外部实现
  index.ts                   # 包公开入口，仅显式导出
```

选择把现有 `cloud` 和本地来源执行统一归入 `sync`，是因为二者共享目标槽位、成功历史和显式重新同步语义。其内部仍保留云端、本地、历史子模块和检查边界，不把现有大类简单拼成更大的同步服务。`library` 提供与传输无关的本机媒体证据，不要求 Emby 在线或已收录才允许识别。

同步内部依赖固定为规则／调度入口可调用 cloud、local、history；cloud 和 local 可以调用 history 的公开接口，history 不依赖前两者，cloud 和 local 互不直接依赖。跨子模块类型归入 sync 的明确契约文件，不通过预览实现文件导出。

每个模块包含明确的 `public.ts`、按需的 `ports.ts`、`persistence/` 和业务文件；`index.ts` 可以仅转发 `public.ts`。公开接口返回业务 DTO，不暴露数据库连接、Repository、整个 DI 容器或其他模块实例。模块内测试就近；跨模块测试位于 Core 的集成测试区域。

依赖方向如下，箭头表示允许直接依赖：

| 调用方 | 可依赖的业务模块公开入口 |
| --- | --- |
| configuration | 无 |
| library | configuration |
| sync | configuration、library |
| ingestion | configuration、library |
| corrections | ingestion、configuration、library |
| delivery | ingestion、library |
| retention | 通过自身窄端口读取需求和证据，不直接依赖上层调度器 |
| bootstrap | 上述模块的工厂、公开接口和各模块命令注册器 |

其他规则：

- `domain` 仅依赖自身与公开契约，不依赖 Node I/O、框架、storage、业务模块或 adapters；保留纯规则测试。
- `files` 只承载文件能力，不读写业务数据库。当前文件重定位日志的持久化依赖通过调用方端口注入；真实文件安全原语保留在这里。
- `adapters` 实现调用方定义的窄端口，bootstrap 注入；不让识别用例直接创建 ParserProcess 或 HTTP 客户端。端口只覆盖已经存在的可替换依赖，不为每个函数生成接口。
- 业务模块不能反向导入 bootstrap；模块之间不能深层导入或通过公共 barrel 重导出私有实现。公共 DTO 优先归 contracts，局部协作类型保留在消费者端口，不把内部类型全部塞进 contracts。
- sync 的完成交接通过其接收者端口注入 ingestion 适配器，ingestion 不反向引用 sync 调度器；retention 的需求快照和清理授权由 bootstrap 连接各所有者接口。
- 跨模块及跨同步子模块禁止包括纯类型在内的循环；单模块内部也禁止运行时循环。现有类型循环应抽取最小共同数据类型解除。

备选方案是保留技术分层目录并新增更多 Service/Repository；这无法解释来源、收据和库内证据的真实归属。也不选择每个业务拆一个 npm 包，避免增加构建和导出维护负担。

### 2. 用表所有权和事务端口限制隐含耦合

默认原始 SQLite 连接仅能出现在 `storage/`、模块 `persistence/` 及专门的测试夹具中。业务用例不能调用 `prepare/exec` 或持有可继续向外传递的连接。Repository 按业务操作提供接口，例如领取操作、保存冻结计划、补记成功，而不是通用 `executeSql`。

| 所有者 | 当前数据事实及迁移来源 |
| --- | --- |
| configuration | `app_setting`、`configuration_directory` 及目录授权／默认配置；业务暂停状态由所属业务模块管理，拆出共享 key 混用 |
| library | 媒体目标身份、Emby 连接／库绑定及库内证据；从 `sources/emby-library-files.ts` 与交付中的绑定管理抽取 |
| sync | 同步规则、作业、账号／绑定、下载项、attempt、提交意图、同步收据与 outbox |
| ingestion | 识别规则／输入、候选、媒体任务、识别编辑、冻结整理计划、COPY 与批次事实 |
| corrections | 修正准备、单条／批次意图、修正历史；变更原媒体事实经 ingestion 的事务端口完成 |
| delivery | 刷新意图、重试和收录状态；媒体任务展示通过投影读取，不再随意跨表写入 |
| retention | 清理预览、逐文件清理意图与恢复日志；成功收据由 sync 保持 |

实施把每张最终基线表登记到唯一所有者，外键并不授予写入权。跨模块只读列表放在明确的 `queries/`，使用只读查询接口；不从只读查询回传原始句柄。可先保持现有字段和事务语义，再收敛重复事实，避免同时改变所有状态定义。

跨模块原子记账由 bootstrap 中明确命名的流程调用同一个同步事务作用域。作用域只携带不透明事务 token；各所有者的持久化实现以此取得同一连接，调用方不能自行执行 SQL。严禁在 SQLite 事务内等待网络或文件 I/O，也不把原子写拆成多个独立提交：

- 下载完成项、成功收据和 outbox 在 sync 内同一事务提交。
- 整理成功、交付意图和必要清理授权通过各所有者事务端口一起记账。
- 修正记录与媒体资产引用更新保留原子性。
- 共享需求释放与清理准入采用同一版本核对／事务，文件删除前仍重新验证证据。

检查器保证连接访问范围、公开出口和表所有者登记完整；它不能仅凭 import 证明任意 SQL 的实际写集合。跨所有者 SQL 写入仍是代码审查必查项，关键事务通过故障注入验证。禁止以 SQL 关键词正则声称完成可靠的 SQL 语义分析。

### 3. 拆流水线时保持执行和恢复共享状态机

`IngestionPipeline` 先成为兼容调用点的内部薄门面，再随调用者迁移移除；终态由 `IngestionService` 提供有限的业务入口。拆分责任如下：

| 单元 | 唯一主要责任 | 当前代码来源 |
| --- | --- | --- |
| 输入与观察 | 来源安装、watcher、稳定窗口、取消与扫描调度 | authorize、watchSource、observe、scanSource |
| 候选接入 | 资产版本、受管成果交接、唯一候选与内容复核 | receive、receiveReceipt、accept、reviewContent |
| 识别用例 | parser／TMDB 协调、选择与季集校验、识别编辑 | recognize、identify、RecognitionEdits |
| 整理计划 | 目标路由、命名、附属文件清单、预览与冻结校验 | buildPreview、accessories、previewScope |
| 整理执行与恢复 | 执行权、COPY、发布、记账、原 intent 恢复核对 | confirm、copy、copyAccessory、auditRestored |
| 批次与自动策略 | 持久批次、公平调度、自动授权 | 已有 RecognitionBatches、OrganizeBatches、AutomaticIngestion |

各单元拥有自己的内存状态，依赖通过构造参数注入，不回传整个父流水线。单元之间只传明确输入、结果和取消信号。观察时钟属于输入观察，复制操作的执行权属于执行单元，不能分别维护两套同名 active 集合。

执行和恢复使用同一持久状态转换及文件证据定义；恢复入口重新核对原 intent，不复用“新建执行”来代替恢复。停止顺序保持先停止接收／触发，再中止等待、等待活动操作到安全点，最后释放文件能力和数据库。请求超时仅结束等待，不把已受理写操作撤销或重发。

备选方案按每 300 行拆成若干文件会保留大对象耦合，甚至让状态分散；本方案按状态所有权拆分并以恢复回归作为通过条件。

### 4. 收敛初始化与旧模型，避免把历史包袱搬入新架构

采用直接初始化的新基线，schema 标识必须高于切换时仓库支持的最大版本；发现基线为 v35，若实施前无其他版本则采用 v36，绝不复用 v1 或 v35 解释新结构。

新 schema 按模块提供 DDL 片段，由 bootstrap 收集并传给 storage，按确定顺序在单个初始化事务建立，核对完整结构、索引、外键和版本；storage 不反向导入业务模块。已有数据库先验证准入，再创建服务／定时器；失败不进行补表、迁移或替代建库。保留跨进程独占、WAL、关闭顺序和当前格式备份。

删除范围以“仅服务旧配置接管”为判据：历史迁移序列、legacy fingerprint／owner 映射、旧来源与独立规则双轨路径、已无当前能力调用的旧契约与跳转。仍承载当前来源身份、共享需求或文件归属的事实必须先建立当前模型所有者；不能仅因名称带 `source_rule` 或 `legacy` 就删除。重新登录后的成功历史确认是当前产品行为，必须保留。

更新 `ManagedUpgradeBackups`：恢复前要求受支持格式匹配，不能先覆盖再等待 Core 拒绝；清单和备份数据库实际结构须一致。原恢复日志必须先安全收敛，格式拒绝不得破坏恢复事务。保留当前格式备份的摘要验证、WAL 一致性和恢复后媒体核对。

Main 仍只管理备份文件与生命周期，不导入 SQLite 打开业务库。备份中的数据库结构由 Core 的受限只读验证模式在隔离暂存副本上核对，返回格式结果；验证模式不创建服务、定时器或初始化表。当前业务写入者停稳后才允许最终恢复，失败不会污染当前状态。

测试改为当前基线构建夹具；保留少量不可兼容旧库／备份拒绝夹具，不再维护完整历史迁移回归矩阵。真实数据清理不是验收前置条件，所有验证可在新隔离目录完成。若用户随后要求重置真实数据，单独列出数据库及关联私有状态范围；不删除媒体，不接管原根标记，不承诺能从新库恢复旧历史。

备选方案只压平 DDL、保留所有运行期接管路径，无法减少核心复杂度；自动清空旧库则不符合操作授权和文件恢复边界。

### 5. Renderer 按功能聚合，Main 和 Core 入口只做组装

```text
apps/desktop/src/renderer/src/
  app/                       # Application、路由、Provider、启动／释放
  features/
    recognition/             # 页面、模型、草稿、专属组件、文案、测试
    sync/
    downloads/
    corrections/
    settings/
    tasks/
    accounts/
    overview/
  shared/                    # 通用 UI、格式化、业务桥客户端、纯工具
```

功能可依赖 shared，shared 不能依赖功能，功能之间不直接导入页面、模型或内部组件；页面组合由 app 或明确的公开展示接口完成。首次抽取不强行把重复轮询统一成基类；只对语义一致、已有多处使用的部分提取小工具，保留代际控制、取消、幂等请求键和释放行为。

草稿 Provider 的位置由导航存活期决定，不能因为移动文件而改成页面卸载即丢失草稿。根样式保留 token／基础布局，业务样式和文案跟随功能；不做全站视觉重设计。`services.ts` 终态仅为 app 组装入口或被移除，所有模型有明确功能归属。

Main 拆为 bootstrap、窗口／生命周期和按能力的 IPC handler。集中保留 sender／frame 信任核验、协议与输入检查、维护模式门禁、错误归一化，再调用静态注册的 handler；不能为“自动分发”暴露任意命令或模块方法。Main/worker/sidecar/logger 的现有职责保持，日志接口随对应边界注入。

Core 的 command 注册按模块提供，不再把所有 `Commands` 手写一遍；用 contracts 动作推导命令类型，显式声明 handler 的满足关系，并继续测试动作与 handler 一一对应。Preload 的明确方法可按能力分文件静态组合，不能新增 `invoke(action: string)` 给 Renderer。

contracts 的 root 入口只显式导出；公共协议、错误、能力 schema 和 DesktopApi 分文件。内部协议仍在 internal，类型声明可从 schema 推导，但避免生成器成为新增维护系统。移除旧动作时同步更新协议版本、Preload、Main、worker、测试和工具；未移除的动作形状与错误语义保持。

### 6. 防腐规则进入本地命令与 PR CI

规则配置是代码仓库内的唯一机器来源，建议置于 `scripts/architecture/`：模块声明、依赖矩阵、表所有者、规模预算和临时例外分文件保存，检查实现复用现有 TypeScript 依赖。文档解释规则和理由，不维护另一份手写导入白名单。

| 检查 | 失败条件 | 关键正反例 |
| --- | --- | --- |
| `format:check` | 活跃代码未符合锁定 Prettier 规则 | TS 装饰器、TSX、CSS 与配置能重复格式化且无语义变更 |
| `check:boundaries` | 进程越界、业务深层导入、反向依赖、禁止循环、连接访问越界、公开入口泄漏实现 | 合法公开导入通过；别名、相对路径、barrel、type-only、require 和动态字面量绕过失败 |
| `check:structure` | 新结构超预算、中央入口定义业务类或访问 SQL、未登记模块／表、过期或扩大例外 | 92 方法类／超长函数失败；声明数据不按函数计量；迁移文件的例外不能通过改名清零 |
| `test:architecture` | 检查器未识别其禁止的样例或误杀允许样例 | 直接调用与 CLI 集成均有正反例，退出码可由 CI 依赖 |
| `check:architecture` | 上述结构／边界／规则测试或模型同步检查任一失败 | 不依赖 Electron GUI、真实数据库或网络，适合快速 PR job |

格式化覆盖活跃 apps/packages 源码与测试、scripts、桌面构建配置；排除 legacy、第三方源码／许可、生成物、二进制和冻结数据夹具。`printWidth: 100` 是排版目标而非切割字符串的硬限制，长 SQL 应按业务语义和持久化封装改善，不改写测试数据来满足宽度。

依赖检查使用 TS 配置和 workspace exports 解析真实目标，覆盖 `import`、`export from`、字面量 `import()` 和 `require()`。受约束区域非字面量模块加载默认禁止；native/parser 必要动态加载只允许精确列明的资源入口。类型依赖同样受模块方向约束，barrel 的导出图也参与检查。现有 Node/Electron/SQLite/私有协议规则保留，并覆盖 Main、worker、Sidecar Host 的职责；测试不能被生产导入，测试自身按归属执行，跨域 fixture 单独限定。

规模预算在统一格式化后计算，初始决策为生产 TS/TSX 文件最多 600 个非空非纯注释行、单个函数／方法最多 100 个同口径行、单类最多 20 个方法。它们是触发职责复查的预算，不声称能度量全部复杂度。数据声明文件通过 AST 判断为类型／声明数据后另计，不给整个目录免检；CSS 不套用函数指标。格式化、删注释或把函数挤成单行均不能降低检查值，结构统计使用标准格式化后的 AST 范围。

存量例外采用精确路径＋规则＋符号／依赖边＋最大值，附原因、负责人角色、关联任务和不超过 60 天的到期日。每项绑定具体修复，不允许通配符、整目录关闭或自动接受新基线。CI 对比 PR 基点：新增、放宽、延长期限的例外默认失败；合理调整规则本身须走明确设计变更与审查，不能在业务 PR 中静默放宽。过期、无对应违规的陈旧例外也失败。PR 基点由 CI 显式传入并获取，缺失时失败；本地支持指定基点，不把浅克隆或 detached HEAD 当作跳过理由。

本轮终态：旧流水线、Main/Core 中央组装、Renderer 模型混放和跨模块数据库访问不留例外；其他被纳入扫描的存量问题必须按精确任务收敛，不能用“后续治理”结项。首次引入基线的提交是唯一初始化例外清单的阶段，后续仅缩减。

增加不受业务路径过滤遗漏影响的快速架构 PR job，检查脚本、规则、格式配置、TS 配置、文档模型变化均可触发；CI 只检查不自动格式化或更新例外。完整桌面工作流仍负责类型、业务及安装态验证。设置远端 required check 属于仓库管理操作，未实际配置前不能声称合并已被强制阻断；实施可交付始终运行且失败的 PR job，并明确报告保护状态。

备选方案依靠 AGENTS.md 或 reviewer 记忆容易遗漏；仅限制 LOC 会鼓励机械拆文件。这里把依赖／数据访问强约束、结构预算和业务故障测试组合使用，也承认机器检查不能替代业务审查。

### 7. 验证与文档绑定到当前实现

维护现有 `docs/architecture/cloud-downloads.c4`，将描述更新为当前配置／同步／识别边界；去掉容易漂移的 schema 数字，版本来源链接到代码。模块清单和模型组件 ID 建立显式映射并检查缺项，拓扑变更同时更新模型；模型语法验证和文档构建不能替代源码依赖检查。

使用现有架构入口解释职责、公开入口、增加用例的路径和事务规则。错误反馈遵循现有约定。实现若需在 AGENTS 添加入口，仅放短链接和必须遵守的边界，不复制整篇设计。本变更规划阶段不修改这些项目文件。

## Risks / Trade-offs

- [范围较大，单次移动难以审查] → 分阶段提交，格式化与逻辑修改分开；移动与必要 import／导出修正作为一个可构建单元。
- [重组 SQL 破坏跨模块原子性] → 按现有事务逐个迁移，先定义所有者和作用域，保留关键故障注入及真实子进程崩溃验证。
- [过多公开接口反而增加跳转] → 仅围绕跨模块依赖和可替换外部能力定义端口，模块内直接组合，不要求每个类都有接口。
- [旧库拒绝影响当前开发实例] → 使用隔离 userData；明确这是破坏性兼容变更，原状态保留，未获授权不执行真实清理。
- [基线清理误删当前成功历史逻辑] → 重新登录确认、成功收据和文件恢复列为显式保留项，现有主规格回归保护。
- [规模阈值产生无意义拆分] → 统一格式化后测量、精确有期限例外、按状态所有权拆分；不以测试数量或行数下降替代行为验证。
- [检查本身被放宽或 CI 被绕开] → 同仓库审查规则变更、基点比较、反例测试、报告远端保护状态；不承诺无法修改仓库规则的绝对防腐。

## Migration Plan

1. **建立可重复基线**：接续当前有效改动，确定行为测试映射、格式规则与结构测量，先接入快速检查和精确存量例外。
2. **明确持久化边界并切换当前模型**：定义目标表所有者及事务接口，建立直接初始化 schema，清除旧配置双轨，更新备份准入／旧动作；同一阶段连同契约、工具与测试形成可运行提交。
3. **重组 Core**：先抽公共叶子能力和数据接口，再迁移同步与成功历史，随后拆 ingestion、修正、交付和清理。每步移除对应旧路径／例外，保持生产只有一套实现。
4. **精简宿主与契约组装**：拆 Main handler、Core 注册器、协议模块；保留统一校验及生命周期顺序。
5. **聚合 Renderer**：按功能逐个移动，拆模型与专属组件，保持路由、草稿和交互不变；取消全局服务混放与业务样式堆积。
6. **收口**：更新模型和文档，清零本轮例外，执行类型、架构、完整业务、桌面与当前平台新构建目录包验证，记录未验证的 OS／正式发行项。

回滚按逻辑提交逆序执行并验证；回滚代码不会回滚已发生的文件操作。跨新旧 schema 的构建各用独立数据目录及匹配备份，不将新库喂给旧构建，也不在回滚时自动删除或恢复用户数据。实施产生的隔离夹具可以按测试生命周期清理，真实数据保持独立授权。
