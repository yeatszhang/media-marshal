# Mac 升级备份与恢复核对

本轮在 macOS 26.5.2、arm64、APFS 验证开发构建。升级备份和数据库恢复不撤销媒体操作；备份范围不含下载目录或媒体库。正式签名、Intel 和 DMG 安装态仍按发行任务分别验收，不能用这里的通过结果代替。

## 启动前与升级前的边界

Core 每次首次启动、手动重启及自动恢复都先经过 Main 的同一检查：处理未完成恢复日志，读取版本元数据，在版本变化时核对旧组件写入者已经退出，等待凭据更新并保存完整私有快照，之后才创建 Core。修复了“首次备份失败后，重启核心可绕过检查”的缺口。检查失败不创建新 Core，业务 IPC 不可用；重试仍须经过检查。检查期间退出后，迟到的成功结果不能创建 Core。

用户主动准备升级时，Main 先停止新接入、账号操作、Core 和 Host，核对本应用的原生进程归属并等待保险箱更新，再保存业务 SQLite／WAL、凭据密文、组件私有状态及版本摘要。失败保持停止状态，提示退出后处理；不会带着半套状态继续写入。快照不进入普通诊断。

Core 打开数据库时使用 SQLite backup API 保存迁移前的一致性备份，未知结构和更高 Schema 拒绝写入。单步迁移事务失败会回滚该步并停止启动。初次备份不会被迁移重试覆盖。业务数据只由 Core 打开；Main 仅在所有写入者停止后复制整包私有文件。

启动前另保存持久标记，Core ready 证明数据库迁移完成后即记录当前版本，再恢复服务凭据和账号。如果进程在这两步之间中断，下次快照标为“数据版本待核对”，不能沿用旧版本元数据假定 Schema 未升级。旧元数据不作为直接降级或绕过 Core 检查的依据。

## WAL 与中断验证

`database.test.ts` 保留旧库连接并禁用自动 checkpoint，在显式清空 WAL 后提交一条设置。测试先证明仅复制主库缺少这条记录，再执行升级，验证迁移前 SQLite 备份包含记录及旧 Schema。原测试先关闭连接，无法证明数据仍仅在 WAL；本轮修正了这个验收条件。

`upgrades.test.ts` 用独立 Electron Node 进程写入并提交 WAL，收到检查点后实际 `SIGKILL`。主库单独复制仍为旧值，完整私有快照包含非空 WAL；修改当前数据后恢复快照，重新打开数据库得到 WAL 中的已提交值。来源文件及现有成果保留。

同一测试组还覆盖恢复替换到一半的异常和实际 `SIGKILL`：下次打开 Core 前，Main 依据持久日志回滚未完成文件组替换。损坏摘要、未来 Schema、平台不兼容和符号链接在正式恢复前拒绝。恢复完成的日志先保存“需要核对磁盘”标记；核对已持久排队后 Main 才确认该标记。

## 恢复后的磁盘核对

受管下载继续使用持久核对队列：原卷和目标文件身份、长度、摘要匹配后才恢复完成；缺盘等待，目标已改动则保留冲突，不重新下载来掩盖差异。

schema v15 增加已整理媒体的恢复核对语义。Core 将已记账主文件及附属文件的核对需求持久化，核对期间任务显示处理中，候选说明正在等待恢复检查。每轮最多处理四个操作；不可访问项后移，原目标授权恢复后继续。该只读核对可以在整理全局暂停时完成，不解除暂停，也不启动 COPY。

核对要求原目标卷／目录与计划一致，并匹配目标 inode、创建时间、修改时间、长度和 SHA-256。全部符合时保留原 inode，将主文件恢复完成，并重新等待独立 Emby 刷新／收录核对；已有网络退避期限不提前。缺失、改写或同内容替换不能认领，主文件转待处理；仅字幕冲突时主文件保持完成，附属项独立失败，作业显示部分失败。所有情况均不改写来源或现存目标，不用备份数据库推断额外文件归属。

核对队列跨 SQLite 关闭重开保留；核对中不允许重试 COPY。Emby 不处理尚待文件核对的任务，迟到收录响应和打开条目响应也不能把它恢复成旧的已收录状态。旧 v14 Core 拒绝 v15，避免忽略这一持久状态；迁移前保留匹配备份，恢复旧数据后仍需重新核对磁盘。

真实文件用例覆盖主文件和字幕正常、同 inode 内容改写、同内容替换 inode、删除目标、字幕独立冲突、目标未授权及跨数据库重开的恢复。缺盘用例是授权暂不可用，不能当作实际物理拔盘验收。

## 复查命令

```sh
npm test -- packages/media-core/src/infrastructure/database.test.ts apps/desktop/src/main/cloud/upgrades.test.ts apps/desktop/src/main/core-supervisor.test.ts packages/media-core/src/ingestion/pipeline.test.ts packages/media-core/src/ingestion/emby-delivery.test.ts
npm run desktop:build
npm run test:desktop -- --grep '升级备份失败|整包升级停写'
```

Electron 验证以隔离用户配置启动真实窗口，在停机状态用一个测试文件占用私有备份目录。启动及手动重启均失败，业务库字节保持；恢复原备份目录后同一窗口可以重启 Core，保留原设置并保存匹配快照。截图为 `test-results/desktop/upgrade-backup-blocked.png`。另一用例从设置触发停写备份、选择恢复，再重开核对数据和下载根；原生确认对话框在测试中为受控替身。

服务密钥另补整应用重开测试，独立新配置可以跨 Main 重启恢复。单个服务密文损坏时，Main 只将该服务视为不可用，仍注入另一项可用服务，保留原密文，并在设置可达的主窗口明确提示需要重新保存的服务；不会将本机解密失败混成远端认证问题。修复其中一项不受另一项解密失败阻断。

真实维护者配置已从 v14 升级到 v15，原来源版本及暂停、文件完成记录保持，目标 inode 和长度未变，没有新增下载或 COPY。整应用重开暴露出既有 TMDB／Emby 密文无法由当前系统保险箱解密，所检查的旧备份也不能解密；交付转为待处理，不能据此宣称当前 Emby 已重新验证。密文保留，待用户在客户端重新保存。独立新配置的跨进程测试通过，仅凭本次现象不能确定旧密文失效原因；[Electron 的说明](https://www.electronjs.org/docs/latest/api/safe-storage#platform-specific-key-providers)要求 macOS 使用一致签名以稳定识别应用，本轮仍为未签名开发构建，不替代签名发行验收。

本次生成的三个私有快照另以独立临时副本读取 SQLite Schema，并先核对清单的文件摘要；其中两个在版本记录修复前误标为 v14，实际为 v15，已校正清单版本，原清单另存本机私有验收目录。原有备份、凭据和媒体文件未修改。新的启动标记防止再次把未完成初始化的旧版本记录当作准确 Schema；无法确认时明确标记未知。

本轮构建、检查与脱敏结果保存到 `tools/desktop-sidecars/fixtures/mac-upgrade-recovery-2026-10-25.json`，不复制个人路径、私有备份内容或凭据。上述 WAL、故障和恢复测试均使用自有临时数据，不在用户真实媒体库制造故障。

最终构建的核心／契约／组件测试 470 项通过、13 项跳过，真实 Electron 窗口回归 22 项通过；类型、依赖边界、构建、OpenSpec 严格检查及文档构建通过。LikeC4 1.60.0 校验并重新导出四个视图，模型更新至 schema v15。
