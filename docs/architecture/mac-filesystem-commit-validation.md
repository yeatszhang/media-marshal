# Mac 文件系统与不覆盖提交验收

2026-10-25 在 macOS 26.5.2（25F84）、arm64 上使用原生驱动挂载独立的 256 MiB 稀疏磁盘映像，核对当前源码的卷授权、来源读取和正式提交。测试未访问用户媒体卷；下表是本机测试结果，不代替 Intel、其他系统版本或实际硬盘拔插验收。脱敏结果与源码摘要见 [JSON 夹具](../../tools/desktop-sidecars/fixtures/mac-filesystem-commit-2026-10-25.json)。

| 文件系统 | 只读来源 | 下载／整理目标 | 原生硬链接 | 独立进程抢占同名目标 | 卸载重挂载 |
| --- | --- | --- | --- | --- | --- |
| APFS（不区分大小写） | 读取与摘要通过，无探测文件写入 | 授权及实际提交探测通过 | 支持 | 三种顺序均保留先占文件 | 原卷／目录身份及管理标记核对通过 |

APFS／HFS+ 的支持仍以每次授权的真实卷身份、目录权限和硬链接能力探测为准；只凭文件系统名称不能跳过检查。其他未验证文件系统、网络卷以及无法建立稳定卷身份的目录不作为支持的写入目标。exFAT 可以作为只读来源，界面会提示改选受支持的下载或整理目标；不会退回覆盖式改名。

## 实际竞争窗口

`ManagedRoot.commit` 先核对已存在目标的归属，再核验暂存文件；发布使用同卷硬链接创建正式路径，目标已存在则失败，不能先删除目标。[Node 的 `fsPromises.link`](https://nodejs.org/api/fs.html#fspromiseslinkexistingpath-newpath) 对应这一原生操作。本轮在提交内部已经查无目标、暂存摘要完成的边界，让另一个 Node 进程以 `wx` 创建目标，再继续正式提交：

- 其他进程先占、内容不同：提交返回冲突，保留对方 inode 和全部内容。
- 其他进程先占、内容相同：仍返回冲突；摘要相同不能证明归属，不自动认领。
- 应用先提交：其他进程的 `wx` 返回已占用，正式文件保留暂存文件 inode。

每例另核对本操作暂存清理不删除正式文件。测试边界由测试代码临时替换摘要方法控制，生产实现没有注入钩子；占位进程真实运行，未把原生 `link` 或写入操作替换成模拟值。此处验证同名文件竞争，静态符号链接逃逸及目录替换另见[目录边界验收](./mac-unified-source-validation.md)，不声称覆盖敌对进程任意改写目录树的全部时序。

## exFAT 只读授权修复

本机 exFAT 的卷 UUID 满足现有契约，但 `getconf PATH_MAX <目录>` 返回退出码 71，底层 `pathconf` 报 `EINVAL`。原流程因此错误地把可读来源标成目录不可用。只读来源现使用 Darwin 的保守 1024 字节路径预算，不依赖卷实现该查询；依据 [Apple `syslimits.h` 的 `PATH_MAX`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/syslimits.h)。写入授权仍使用原卷能力探测和文件系统白名单，没有放宽 exFAT 写入。

修复后重新执行三种文件系统的完整矩阵，均符合上表；exFAT 来源内容与目录成员保持不变。卷身份和 Schema 不变，无新增数据库迁移。

## 重复执行

先完成 `npm run desktop:build`，再指定一个**尚不存在**的本机私有报告路径：

```sh
node tools/desktop-sidecars/check-commit-filesystems.mjs /绝对私有路径/本次验收.json
# 可在末尾加 APFS、HFS+ 或 exFAT，只验证其中一种。
npm test -- apps/desktop/src/main/cloud/no-overwrite.test.ts apps/desktop/src/main/cloud/roots.test.ts
```

工具只在自己创建的私有临时目录生成映像和测试文件；按映像的精确绝对路径核对设备后卸载，确认全部卸载及所有者标记后才删除临时目录。失败则保留私有报告和未能安全清理的目录，不按设备名猜测、卸载其他卷或清理来源。报告以 `wx`、0600 创建，含本机私有路径及有界错误详情；分享前只能导出白名单字段，不能直接提交原报告。本轮全部映像已卸载，临时目录已清理。
