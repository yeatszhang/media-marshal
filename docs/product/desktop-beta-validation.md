# Mac 内测招募与验证准备

本页是 `add-local-desktop-emby-ingestion` 的 9.3 准备材料，包含招募草稿、记录口径和访谈提纲。材料已准备不代表招募已经开始，也不代表当前工作区已有可发放的安装包。正式发放前，以对应版本的安装态验收、架构和签名状态为准。

## 本轮要验证什么

先验证已有 Emby 用户能否独立完成配置，让一个真实文件整理并被 Emby 收录，再观察下一次新增内容时是否继续使用。记录卡住的位置和维护者实际花费的支持时间。

按设计计划访谈 10～15 人，邀请约 20 位符合条件的 Mac 用户。覆盖夸克应用内下载、夸克客户端本地目录、自定义本地目录三条路径。优先使用已完成相应安装验收的架构；尚未验证的架构进入候选名单，不能拿另一架构的结果代替。

计划门槛是至少半数合格受邀用户无需实时协助完成首次收录。这是本轮实验目标，不是已有成绩。样本不足时报告实际人数，不将维护者验证、自动化测试或重复补扫计入外部用户成功数。

## 发放前核对

- 安装包对应本轮代码，已完成该架构的安装态与功能验收；填写版本、架构、SHA-256 和签名状态。不发放旧安装包演示尚未包含的功能。
- 参与者已有可用 Emby、本人 TMDB Key，以及相互独立的下载／输入和媒体目标目录，理解 COPY 会占用额外空间。
- 首轮仅选一部电影或一集普通剧集。官方客户端本地目录由用户先确认下载完成，整理仍经过观察、识别预览和人工确认。
- 提供该版本的操作说明和已知限制，确认记录方式及后续跟访意愿。系统阻止安装时记录提示并停止该轮安装，由维护者处理产物问题后另开尝试。

当前桌面范围不包含新用户 Emby 自动安装、其他网盘客户端行为保证、非 macOS 安装或官方付费 API。批量确认、修正等能力只有在对应版本实际验收后才能加入试用范围。

## 招募说明草稿

> **Media Marshal：你的本地媒体库**
>
> 我们准备邀请一批 Mac 用户，试用下载文件整理到已有 Emby 媒体库的流程。希望了解：配置是否容易、第一次入库会卡在哪里，以及下次新增文件时是否还愿意继续用。
>
> 如果你已经在用 Emby，平时通过夸克下载或整理本机影视文件，愿意先拿一部电影或一集剧集试用，可以参与本轮内测。现阶段需要自备 TMDB Key，并在客户端填写已有服务配置。
>
> 首次按文档独立操作，记录完成情况和卡住的位置；需要帮助时随时说明。之后约一周，再反馈有没有新增内容、是否再次使用，以及遇到的问题。应用默认 COPY 并保留来源文件，下载目录与媒体库目录需要分开。
>
> 参与记录默认留在本地。分享反馈时只需提供版本、阶段、耗时和脱敏错误类型，不需要媒体名称、完整目录、账号 Cookie 或服务密钥。分享截图或额外诊断前，可以先检查并遮蔽个人信息。
>
> 安装包版本、适用架构、签名状态、下载方式和反馈渠道会在本轮实际开放时单独给出。便捷、完整的整理核心保持免费；本轮不涉及购买桌面授权或更新续费。

发放时补齐真实版本、可用渠道和观察日期；没有实际发布的信息保持未填写，不用占位下载链接代替。

## 记录与分组

每位参与者使用本地编号，每次尝试另编号。首次失败、请求帮助和重试均保留原记录。联系信息与过程记录分开维护，仓库模板不保存联系映射。

招募前的筛查也记录人数和原因，例如尚无 Emby、没有 TMDB Key、架构暂未支持。未满足前置条件的人不计入合格试用样本，但需单独报告，避免将配置门槛隐藏在成功率之外。

按来源路径、系统／架构、是否熟悉媒体库、存储类型分组；不收集账号名称、IP、机器名、媒体清单或绝对路径。文件数量和大小范围已足够描述样本，文件名可用“样本 A”。

使用[首次入库记录模板](./desktop-beta-first-run.md)。失败记录至少包含阶段、用户看到的原因、已尝试的处理、是否需要帮助和最终结果。日志／截图按自愿、最小范围提供；原始数据库、凭据文件和私有备份不作为普通反馈材料。

## 时间与成功口径

| 时间点 | 定义 |
| --- | --- |
| T0 | 本次开始安装；工作区启动另标“不适用” |
| T1 | 首次正常打开窗口且核心可用 |
| T2 | 来源和目标已确认，已有 Emby 连接／库映射验证通过，所需元数据配置已保存 |
| T3 | 首个样本完成下载并开始稳定观察；既有本地文件从开始观察计时 |
| T4 | 首个样本识别完成，用户可核对作品、季集和 COPY 预览 |
| T5 | 文件已整理完成，来源保留 |
| T6 | Emby 对应文件的收录证据通过 |
| T7 | 可选：在常用播放器实际开始播放；与收录分别记录 |

时间记录注明时区，同时记录自然耗时、主动操作分钟、后台等待分钟和中途离开分钟。下载、稳定窗口、COPY 和 Emby 等待分别说明；不为改善结果扣掉真实卡顿。没有记录的时间填“未记录”，不能补成零。

只下载成功、文件 DONE、发出刷新请求或在库中看到同名条目，都不等于完成 T6。安装配置成功还须通过首次真实识别确认元数据配置可用；首次入库以 T6 为准。播放器验证单独统计，不用收录状态推定已经能播放。

独立完成允许阅读随包文档和使用产品内提示。接受实时讲解、远程操作或针对该次问题的个别指导后，后续结果归为“有协助完成”；保留已经独立完成的前序阶段。请求帮助不会删除原失败尝试，也不把协助完成改写为独立成功。

## 指标表

| 指标 | 口径 |
| --- | --- |
| 独立安装成功率 | 无实时协助达到 T1 的人数／已开始安装的合格参与者人数 |
| 独立配置成功率 | 无实时协助完成 T2 且首次识别返回有效结果的人数／已开始安装的合格参与者人数；单列安装与配置失败 |
| 独立首次收录 | 无实时协助达到 T6 的人数，同时报告占合格受邀人数和已开始尝试人数的比例；约 20 人中至少半数为计划目标 |
| 首次入库耗时 | T6−T0；已安装用户另报 T6−T2。只对有完整时间的成功尝试汇总，另报缺失时间、失败和未完成数量 |
| 首次配置放弃率 | 开始配置后、观察期内明确放弃且未完成配置的人数／开始配置人数；尚在等待和失访单列 |
| 一周持续使用 | D2～D7 有新增内容并再次完成整理／收录的人数；分别报告其占首轮成功人数、以及首轮成功且期间有新增内容人数的比例 |
| 人工修复 | 修改作品／季集、解决路径冲突或恢复失败的次数，按阶段分类；本版正常的人工确认单列，不当作误识别或修复 |
| 支持成本 | 按人、按故障记录主动支持分钟及往返次数，包含最终失败者；同时报告总分钟／受邀用户数和总分钟／持续使用用户数，分母为零时不计算 |

所有比例一起列出分子、分母和未反馈人数。小样本优先展示逐人结果和中位数、范围，不只报告平均值；不得用下载复用、页面访问或再次打开应用代替持续新增入库。没有新增内容的人保留在队列中，说明其没有再次使用机会。

## 首次访谈提纲

1. 回忆最近一次收片或追剧：从哪里下载、多久整理一次、通常耗时多少？现有工具和手工步骤是什么？只记录流程和数量，不要求提供媒体清单。
2. 看完说明后，哪些准备已经具备，哪些需要另外学习？Emby、TMDB Key、输入与媒体目录分别在哪里造成困惑？
3. 独立操作时，请在需要帮助的地方停下。你原本预期下一步是什么，实际提示是否足以继续？先记录原始困难，再提供帮助。
4. 识别预览中，哪些信息让你敢确认 COPY？有没有发现错误作品、季集、目标路径或重复内容？为修正它花了多少时间？
5. 文件整理完成和 Emby 收录之间的等待是否清楚？发生错误后，你能否判断该重试下载、整理还是交付？
6. 与原来相比，哪一步省了时间，哪一步增加了负担？如果明天继续用原来的方案，实际会怎么做？
7. 如果以后有免配置的官方识别服务，什么问题需要先解决才值得尝试？过去是否为类似服务付过费，可按范围自愿回答；不收集订单或支付信息。
8. 如果需要付费，你更可能按需使用还是持续订阅，理由是什么？将“愿意考虑”和实际购买分别记录。当前不收款，也不把口头好评当作付费证据。

访谈观察真实过程时，由参与者控制演示范围，优先使用脱敏样本。未经另行确认，不保存原始目录截图、媒体名或完整日志。

## 一周跟访与决策

跟访先问是否有新增内容，再问是否再次使用、完成了几次、是否需要人工修复，以及继续或放弃的具体原因。把没有新增、尚未使用、尝试失败和仍在使用分别记录。

复盘按三条来源路径查看掉点、耗时和支持分钟。独立首轮没有达到计划目标时，先定位安装、凭据、目录、识别或恢复问题，再选新的尝试验证；不以增加人工陪同提高“独立成功率”。

商业验证遵循[既定路线](./business-and-operations.md)：先验证免费整理工具的持续价值，后续官方识别 API 的价格和额度另做实验，会员和托管通知再独立规划。此材料不增加遥测、账户、支付或通知服务。
